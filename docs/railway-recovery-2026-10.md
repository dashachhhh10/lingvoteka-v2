# Lingvoteka: восстановление Railway после инцидента 21–22 октября 2026

Обновлено 23 октября 2026, 11:45 UTC+08. [Railway восстановил сборки и деплои для Trial](https://status.railway.com/). Коммит `f44b595` из `dev` автоматически развернулся на Vercel и в Railway API/worker: все три статуса GitHub — success. Публичный `/api/health` вернул `revision: f44b595cb53b5119812697720545c18a40ccdd7a`; новый маршрут свободной практики без сессии вернул 401. [Railway сбросил GitHub-токены и ключи всех бакетов](https://blog.railway.com/p/security-disclosure-recommendation-redeploy-buckets-and-reconnect-github-after-the-credential-reset), поэтому успешные статусы не заменяют проверку S3 и настроек. Не считать этап 5 завершённым, пока оставшиеся проверки ниже не пройдут.

1. Когда Railway снова разрешит сборки Trial, войти в [проект Lingvoteka](https://railway.com/project/0b87569c-2afb-49a3-a6ea-d96706e9d753). В Account Settings переподключить GitHub; проверить доступ Railway GitHub App к `dashachhhh10/lingvoteka-v2`. У сервисов `api` и `worker` в Settings → Source проверить этот репозиторий, ветку `dev` и включённый Auto Deploy. Railway [описывает эти шаги](https://blog.railway.com/p/security-disclosure-recommendation-redeploy-buckets-and-reconnect-github-after-the-credential-reset). Если автоматический деплой не стартует, для каждого сервиса выбрать **Deploy Latest Commit**; во время инцидента обычный **Redeploy** может быть недоступен.
2. У обоих сервисов проверить, что `DATABASE_URL` остаётся ссылкой на PostgreSQL, а `S3_ACCESS_KEY_ID` и `S3_SECRET_ACCESS_KEY` — ссылками на Bucket, не скопированными старыми значениями. Им нужны также `FILE_STORAGE=s3`, `S3_BUCKET`, `S3_REGION`, `S3_ENDPOINT`, `S3_FORCE_PATH_STYLE=false`. Новые ключи бакета появятся в Railway автоматически, но работающие контейнеры получат их только после нового деплоя. Не переносить значения ключей в Git или чат.
3. [Railway рекомендует сменить все секреты, хранившиеся в переменных окружения](https://blog.railway.com/p/security-disclosure-wednesday-october-21st). Для Lingvoteka это прежде всего `GEMINI_API_KEY`, `BETTER_AUTH_SECRET`, `REGISTRATION_INVITE_CODE` и пароль PostgreSQL; старые `RESEND_API_KEY`/`SMTP_PASSWORD` удалить или обновить, если они ещё сохранены, хотя отправка почты выключена. Смена `BETTER_AUTH_SECRET` завершит прежние сессии пользователей. Пароль PostgreSQL менять через **Postgres → Database → Config → Regenerate**, а не ручной правкой переменной или SQL; затем заново развернуть `api` и `worker`. [Инструкция Railway по PostgreSQL](https://blog.railway.com/p/security-disclosure-recommendation-rotate-postgresql-database-credentials) предупреждает о кратком разрыве соединений. Если локальная разработка подключается к Railway PostgreSQL, обновить её локальную строку подключения отдельно.
4. После успешных деплоев открыть [публичный healthcheck](https://lingvoteka.vercel.app/api/health). Ответ должен содержать `status: "ok"` и `revision`, совпадающую с текущим SHA `origin/dev`. Ответ только с `status` означает, что отвечает старый API. В Railway проверить статусы и логи **обоих** сервисов, отсутствие ошибок подключения к PostgreSQL и бакету. Затем через отдельный синтетический аккаунт загрузить небольшой JPG, дождаться AI-черновика, подтвердить данные, скачать исходный файл, пройти карточку и упражнение; удалить синтетические данные. Настоящий урок проверить отдельно вместе с владельцем аккаунта.
5. После восстановления сделать ещё один обычный коммит в `dev` и подтвердить, что Vercel, Railway API и worker обновились **автоматически**. Проверить журналы и бакет на необычные операции по [рекомендациям Railway](https://blog.railway.com/p/security-disclosure-recommendation-redeploy-buckets-and-reconnect-github-after-the-credential-reset). Встроенные резервные копии PostgreSQL пользователь решила пока отложить; это ограничение остаётся открытым.

Не публиковать ключи, пароли, содержимое `.env` или личные материалы уроков в отчётах о проверке. Публичная версия считается восстановленной только после проверок API, worker, PostgreSQL и бакета, а не по одному ответу healthcheck.
